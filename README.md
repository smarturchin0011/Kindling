# Kindling 火种

> **上下文不是想出来的，是做出来的。**
> 所以行动不是上下文的下游产物 —— 行动是获取上下文的唯一手段。

给「擅长宏观思考、但因追求完备的顶层设计而无法启动」的人用的上下文引擎。

## 它解决什么

不是"思维混乱"。是**思维过度有序** —— 想法接得太好，形成一个自洽但无法启动的完美闭环。

这两种病的处方相反：给混乱者结构 = 解除阻塞；给过度有序者结构 = **加重病情**（一个漂亮框架会产生认知闭合的满足感，替代行动）。

所以 Kindling 的唯一输出是「你接下来 5 分钟做什么」。结构是副产品。

## 快速开始

```bash
uv sync --extra dev
uv run python -m kindling          # → http://127.0.0.1:8777
```

```bash
uv run pytest tests/ -q            # 100 passed，零网络依赖
```

## LLM 调用与模型设置

**Provider：** OpenRouter — `POST https://openrouter.ai/api/v1/chat/completions`

**API Key：** 从项目根 `.env` 读 `OPENROUTER_API_KEY`；找不到会自动回退到
`~/AppData/Local/hermes/.env`。改 key 需重启服务。

**模型：点右上角「设置」，改完立即生效，不需要重启。**

设置面板可调：

| 项 | 说明 |
|---|---|
| 模型 | 8 个预设一键切换，或手填任何 OpenRouter 模型 id |
| 测试连通 | 发一个最小请求，验证模型可用 **且能干净返回 JSON** |
| Temperature | 0–2。缺口检测建议 0.3–0.8 |
| 完整度阈值 | 默认 60%。调低更容易拿到框架 —— 但那正是「漂亮空框架」的来源 |
| 最少证据 / 约束条数 | 闸门的结构性下限 |

设置存在 `settings.json`（与 `state.json` 同目录）。

> **为什么「测试连通」要单独验 JSON：** 换模型最大的坑是某些模型不遵守
> "只输出 JSON"，跑到缺口检测一半才炸。这个按钮让你 5 秒内验出来。

`KINDLING_MODEL` 环境变量仍受支持，但只在首次启动（还没有 settings.json 时）生效，
之后由设置面板接管。

## 六层架构

```
L1 采集      碎片输入，280 字上限，输入时 0 个结构决策
    ↓
L2 上下文层  ★真正的资产。带类型条目 + 权重
             证据5.0 > 约束3.0 > 事实2.0 > 意图1.0 > 偏好0.5
    ↓ 读                                        ▲ 写入证据
L3 缺口层    ★护城河。交互方向反转 ——            │
             不是用户提问LLM回答，而是LLM提问用户回答  │
    ├── 能凭记忆答 → 追问一句 → 回 L2            │
    └── 只能靠行动答 ↓                          │
L5 收窄层    唯一一个 Move（≤5min，全局只允许1个）  │
    ↓ 用户真的做了                              │
L6 回流层    产出物 → 证据条目 ────────────────────┘
    ↓
L4 综合层    完整度 ≥60% 才允许 → 2-3 个竞争框架
```

**飞轮（L6→L2）是全部的关键：** AI 笔记的上下文是静态的，Kindling 的上下文是**复利**的。

## 四个硬机制（代码级强制，不是建议）

| 机制 | 实现 | 防止什么 |
|---|---|---|
| 降级承诺 | Spark ≤280 字，输入时零分类决策 | 物理上无法在第一步写设计文档 |
| 竞争框架 | 一次必须 2-3 个，每个显式声明 `优化/牺牲` | 单方案引发"不够好我要改"的无底洞 |
| 完整度闸门 | <60% 时 synth 拒绝执行（HTTP 423） | 上下文薄时拿到漂亮空框架（麻醉剂） |
| 结构必须过收窄层 | pick 后强制推导出 Move | **认知闭合替代行动** |

第四条最重要：**看到漂亮结构在机制上不是一个可以停下来的状态。**

## 内部 Log

每次 LLM 调用记录完整 system prompt / user prompt / 原始响应 / 耗时 / token。
前端底部面板可展开查看。存在内存 ring buffer（400 条），服务重启清空。

这不是调试设施，是产品功能 —— 你要验证"LLM 提问比我自己写 prompt 更有效"这个假设，
必须能看见它到底收到了什么、算出了什么。

## 真实验证记录

用真实议题「如何系统地教别人 AI 产品知识」跑真实 LLM：

**第 1 轮（只有 3 条抽象意图）问出的问题：**

> 上一次你试图教某个人 AI 产品知识，他当场问了什么让你卡住的那个点是什么？
>
> 为什么关键：你说「教别人最难的是他们没有直觉判断力」，但**这是个二手结论**……
> 没有这个，任何「系统教学法」都只是**你脑补出来的理想情况**。

**飞轮完整度变化：** 20% → 45% → 70% → 85%（闸门开启）

**闸门开启后的框架带真实 tradeoff 且引用了具体事故：**

```
反直觉纠偏框架              基于证据 4 条
  ✓ 防止灾难性决策（如「等100%再上线」）
  ✗ 可能让人觉得AI「全是坑」而过度保守
```

## 开发中修掉的真实缺陷

1. **`render_context` 排序错误** — 按枚举声明顺序迭代，最贵的 evidence 排最后给 LLM 看。改为权重降序。
2. **闸门条件自相矛盾（最严重）** — `SATURATION=30` 时结构最小值（13分）只有 43%，永远过不了 60%。用户补齐提示要求的东西闸门却打不开，摧毁信任。`test_gate_criteria_are_consistent` 永久锁住这个不变量。
3. **闸门与缺口检测器没联动** — 真实跑到 70% 时发现：LLM 连问两轮 evidence，而唯一卡点是"缺 1 条约束"。现在把 `gate.missing` 喂进 prompt。

## 明确不做（YAGNI）

数据库 / 向量检索 / 多议题 / 协作 / 云同步 / 移动端 / 语音输入 /
自动导入聊天记录 / LLM 打完整度分（会漂移，闸门必须确定性）

MVP 刻意用 CLI 级技术栈（单文件 JSON + 零构建前端），因为最大的风险
不是技术风险，是**这个产品自己变成一个完美主义陷阱**。
